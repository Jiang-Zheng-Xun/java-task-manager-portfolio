# NoDB — Pure test database configuration validator

Date: 2026-10-25
Base: e0973f1f65c0f1e52fa6cb484b4fc1883bdf4be9

## Scope

Add a pure Java test-support component that compares an explicitly
supplied settings snapshot against an independent expected-target policy.

Reuse TestDatabaseMode for exact local/ci parsing. Do not trim,
case-fold, normalize, decode URLs or resolve DNS names.

Success means configuration matches the supplied policy only.
It does not grant permission to connect or verify database identity.

## Implementation

Two new files under
src/test/java/io/github/jiangzhengxun/taskmanager/support/testdb/:

- TestDatabaseConfigValidator.java
- TestDatabaseConfigValidatorTest.java

The validator checks these error categories in order:

1. MODE_REJECTED
2. POLICY_MISSING
3. POLICY_INVALID
4. CONFIG_MISSING
5. URL_UNSUPPORTED
6. TARGET_MISMATCH

A null snapshot is treated as a null mode and rejected.

Supported URLs are deliberately restricted to an explicit PostgreSQL
JDBC host, port and database form. The contract defines ASCII DNS/IPv4,
port and database lexical rules and requires exact target comparison.
Unsupported forms and missing rules are rejected without fallback.

The component accepts no password and produces fixed diagnostic
results. Snapshot and expected-target string representations are
redacted. Exceptions originating in arbitrary caller-supplied Map
implementations are outside this diagnostic-redaction guarantee.

The existing three C1 files remain unchanged.
No production source, dependency, POM, CI, Compose, application
configuration or database schema was changed.

## Reflection

### Verified outcome

The configuration contract was explicitly approved, implemented through
one bounded model invocation, independently reviewed and validated with
targeted offline JUnit execution.

### Technical learning

Configuration equality, actual database identity and permission to
connect are separate concerns.

A narrow URL contract avoids implicit normalization and fallback, but
must state unsupported formats explicitly.

Diagnostic redaction covers values generated by this component.
It cannot guarantee the contents of exceptions thrown by arbitrary
external implementations.

### Problems and resolutions

The formal local repository lacked the fixed base object.
Preparation stopped, and an explicitly authorized external clone
obtained and checked out the exact commit.

The first authentication preflight checked isLoggedIn, while the CLI
returned loggedIn. It stopped before any model call. A read-only,
redacted diagnostic identified the mismatch.

A Python replacement fragment was mistakenly presented without a
complete execution wrapper and was pasted into zsh, which rejected it.
The corrected delivery used a complete Python heredoc.

These preparation failures did not consume the authorized model call.
The subsequent single model invocation exited successfully.

### Process improvements

Verify actual CLI field names before constructing gates.
Provide complete executable commands rather than isolated replacement
fragments. Bind delivery and test evidence to a fixed base and hashes.

Authentication checks, manual handoffs and corrective work remain
process costs. No comparison baseline supports an efficiency claim.

### Reusable learning candidate

Explain why configuration validation, database isolation, Spring
lifecycle ordering and zero-connection evidence require distinct checks.

No Question Bank update or independent mastery assessment is implied.

## Boundaries and follow-up

This component does not read environment variables, create DataSource
or Flyway objects, execute SQL or start Spring.

Actual dedicated test targets and their allow rules still require
approval and verification. The local dedicated-container policy and
CI job-service policy have not been implemented by this delivery.

Custom DataSource/Flyway detection and support boundaries remain
unresolved for integration. Initializer ordering and zero-connection/
zero-migration behavior have not been demonstrated.

Existing database tests are not yet protected by this component.
The complete guard and Evidence API are outside this delivery.

Private operational paths, authentication details and raw CLI records
remain outside the repository. Dynamic PR/CI, merge, cleanup, final
work time and Issue closure belong in the Issue and authorized closure
records, not later amendments to this stable log.
